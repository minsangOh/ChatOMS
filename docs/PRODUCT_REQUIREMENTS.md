# 크로스플랫폼 AI 코딩 하네스 데스크톱 앱 개발 요청

## 1. 역할

당신은 시니어 데스크톱 애플리케이션 아키텍트이자 Rust, Tauri 2, React, TypeScript 개발자다.

이번 작업의 목표는 공식 Claude Code CLI와 공식 Codex CLI를 로컬에서 조율하고, Gajae-Code 방식의 개발 하네스 워크플로를 제공하는 크로스플랫폼 데스크톱 애플리케이션을 설계하고 구현하는 것이다.

처음부터 코드를 작성하지 말고 다음 순서로 진행하라.

1. 요구사항 분석
2. 기술·정책상 불확실한 부분 조사
3. 시스템 아키텍처 설계
4. 데이터 모델과 상태 전이 설계
5. 보안 및 승인 정책 설계
6. MVP 구현 계획 작성
7. 사용자에게 설계 결과 보고
8. 고위험 설계 변경이 있을 때만 사용자 승인 요청
9. 승인된 범위에서 구현 시작

명시되지 않은 요구사항을 임의로 추가하지 말고, 불확실한 내용은 가정으로 표시하라.

---

# 2. 제품 목표

다음의 순차적 개발 흐름을 GUI에서 실행하는 로컬 데스크톱 앱을 만든다.

```text
사용자 작업 입력
→ Claude 요구사항 분석 및 설계
→ Codex 구현
→ 빌드 및 테스트
→ 테스트 실패 시 Codex 자동 수정
→ Claude 최종 리뷰
→ 중대 문제 발생 시 Codex 재수정
→ 사용자 diff 검토
→ 기본 브랜치 병합
→ 작업 기록 보관
```

Gajae-Code는 인증 프록시나 모델 API 변환기로 사용하지 않는다.

Gajae-Code에서 참고할 핵심은 다음 하네스 워크플로다.

* 요구사항 인터뷰
* 목표 명확화
* 작업 계획
* 단계별 구현
* 검증
* 리뷰
* 수정
* 완료 판정

# 3. 지원 플랫폼 및 기술 스택

## 3.1 지원 플랫폼

우선순위는 다음과 같다.

1. Windows 10·11
2. macOS

Linux는 MVP 필수 지원 대상이 아니다.

## 3.2 기술 스택

* 데스크톱 프레임워크: Tauri 2
* 프런트엔드: React + TypeScript
* 백엔드 및 로컬 오케스트레이터: Rust
* 로컬 데이터베이스: SQLite
* 작업 산출물 저장: 로컬 파일 시스템
* 버전 관리 격리: Git branch + Git worktree
* AI 실행:

  * 공식 Claude Code CLI
  * 공식 Codex CLI
* 인증:

  * 각 PC에 설치된 공식 CLI의 로그인 상태 사용

Python 기반 상시 백엔드 서버나 별도의 웹 서버를 기본 구조로 두지 않는다.

# 4. 인증 및 계정 정책

앱은 OAuth 토큰, 세션 쿠키, 비밀번호 또는 CLI 내부 인증정보를 직접 읽거나 저장하지 않는다.

다음 행위를 금지한다.

* Claude 또는 Codex 토큰 추출
* 브라우저 쿠키 탈취
* 공식 OAuth 흐름 우회
* OAuth를 임의 API 프록시로 변환
* 다중 계정 풀링
* 계정 한도 우회
* 비공식 인증정보 재사용
* 인증정보 로그 출력

앱은 각 장비의 공식 Claude Code CLI와 Codex CLI 로그인 상태를 사용한다.

계정 전환이 필요하면 공식 CLI 로그인 절차를 실행하도록 안내한다.

## 4.1 앱 프로필

앱 내 프로필 전환을 지원한다.

프로필별로 분리하는 항목:

* Claude CLI 인증 프로필 참조
* Codex CLI 인증 프로필 참조
* 회사·개인 계정 구분
* 프로필 표시 이름

공통으로 유지하는 항목:

* 프로젝트 목록
* UI 설정
* 승인 정책
* 작업 기록 구조
* 일반 앱 설정

프로필은 특정 장비에 고정하지 않는다.

# 5. 핵심 아키텍처

다음 계층 구조를 기준으로 설계한다.

```text
Desktop GUI
  └─ Local Orchestrator
      ├─ Harness Orchestrator
      ├─ Internal Harness Workflow Engine
      ├─ Claude Provider Adapter
      ├─ Codex Provider Adapter
      ├─ Model Recommendation Engine
      ├─ Context Package Builder
      ├─ Approval Policy Engine
      ├─ Session Manager
      ├─ Task State Machine
      ├─ Git/Worktree Manager
      ├─ Command Execution Sandbox
      ├─ Test Runner
      ├─ Review Coordinator
      ├─ Network Policy Engine
      ├─ Secret Redactor
      ├─ Audit Log
      ├─ Recovery Manager
      └─ Update Manager
```

Internal Harness Workflow Engine은 Gajae-Code에서 참고한 요구사항 명확화, 계획, 단계별 구현, 검증, 리뷰, 수정과 완료 판정의 workflow 개념을 ChatOMS 내부에서 소유한다. 외부 Gajae-Code 저장소, adapter 또는 protocol에는 의존하지 않는다.

OS별 기능은 인터페이스로 추상화한다.

예시:

```rust
trait PlatformService {}
trait ProcessRunner {}
trait ShellAdapter {}
trait PathResolver {}
trait FilePermissionService {}
trait NotificationService {}
trait UpdateService {}
trait DiskEncryptionStatusService {}
```

Windows와 macOS 구현을 분리하되 상위 비즈니스 로직에는 OS별 조건문이 무분별하게 확산되지 않도록 한다.

# 6. 작업 모드

## 6.1 일반 작업 모드

단순 질의, 코드 분석, 작은 수정 등에 사용한다.

Gajae-Code 하네스 전체 단계를 사용하지 않고 Claude 또는 Codex를 직접 실행할 수 있다.

일반 작업 모드는 MVP 핵심 범위가 아니다.

## 6.2 하네스 모드

복잡한 개발 자동화에 사용한다.

기본 역할 순서는 다음과 같다.

```text
Claude 설계
→ Codex 구현
→ Claude 리뷰
```

Claude는 기본적으로 다음을 담당한다.

* 요구사항 분석
* 코드베이스 구조 분석
* 설계
* 구현 계획
* 위험 식별
* 최종 코드 리뷰

Codex는 기본적으로 다음을 담당한다.

* 파일 생성 및 수정
* 구현
* 리팩터링
* 테스트 작성
* 테스트 실행
* 빌드
* 리뷰 지적 수정

Claude는 기본적으로 읽기 전용으로 동작한다.

Claude가 코드를 직접 수정하는 기능은 MVP에서 구현하지 않는다.

## 7.1 MVP 포함 기능

* 로컬 프로젝트 등록
* 프로젝트 유효성 검사
* Git 저장소 감지
* Git이 아닌 폴더의 사용자 승인 후 초기화
* Claude 설계 실행
* 고위험 설계 승인
* 작업별 Git branch 생성
* 작업별 Git worktree 생성
* Codex 구현
* 빌드 및 테스트

* Claude 최종 리뷰
* 중대 문제 자동 재수정 최대 1회
* 사용자 diff 검토
* 사용자 승인 후 기본 브랜치 자동 병합
* 안전한 병합 충돌 자동 해결
* 작업 기록 저장
* 민감정보 마스킹
* 비정상 종료 복구
* 병합 후 worktree 보존 및 자동 정리
* 앱 업데이트 확인 및 안전한 롤백

## 7.2 MVP 제외 기능

* 다중 프로젝트 동시 실행
* 병렬 하위 작업
* 여러 AI의 동시 파일 수정
* 원격 Git 쓰기
* 자동 push
* PR·이슈·릴리스 생성
* 배포 자동화
* 플러그인 시스템
* 팀·조직 기능
* 사용자 간 작업 공유
* 클라우드 동기화
* 외부 서비스 연동
* Telegram 또는 모바일 원격 제어

* 중앙 서버

MVP 구조는 향후 확장이 가능해야 하지만, 제외 기능을 선제 구현하지 않는다.

# 8. Git 및 worktree 정책

모든 코드 변경은 별도 Git worktree에서 수행한다.

원본 작업 디렉터리는 기본적으로 읽기 전용으로 취급한다.

## 8.1 Git 프로젝트

작업 시작 시 다음 절차를 수행한다.

```text
현재 브랜치 및 Git 상태 확인
→ 기준 커밋 기록
→ 작업 브랜치 생성
→ 전용 worktree 생성
→ worktree에서만 AI 작업 수행
```

브랜치 이름은 충돌 가능성이 낮고 작업을 식별할 수 있도록 생성한다.

예시:

```text
ai-task/<date>-<short-task-id>
```

## 8.2 Git이 아닌 폴더

Git 저장소가 아닌 폴더에서는 자동으로 `git init`을 실행하지 않는다.

다음 내용을 사용자에게 표시한다.

* Git 초기화 목적
* 생성될 `.git` 디렉터리
* 초기 스냅샷 커밋 생성 여부
* 제외 파일 확인 필요성
* 기존 파일에 미치는 영향

사용자 승인 후에만 다음을 실행한다.

```text
git init
→ .gitignore 확인 또는 생성
→ 초기 스냅샷 커밋
→ 작업 브랜치 생성
→ worktree 생성
```

# 9. 설계 승인 정책

Claude의 설계가 완료되더라도 모든 작업에서 승인을 요구하지 않는다.

다음과 같은 고위험 설계가 포함될 때만 구현 전 승인을 요청한다.

* 아키텍처 변경
* 데이터베이스 스키마 변경
* 인증·권한 구조 변경
* 보안 정책 변경
* 외부 네트워크 동작 추가
* 외부 전송 추가
* 대규모 파일 이동 또는 삭제
* 공개 API 또는 저장 형식 변경
* 운영체제 설정 변경
* 관리자 권한 필요
* 기존 호환성을 깨는 변경
* 데이터 마이그레이션
* 복구가 어려운 변경

일반적인 기능 구현, 프로젝트 내부 파일 수정, 테스트 추가 등은 설계 후 자동으로 구현 단계로 진행할 수 있다.

# 10. 모델 추천 정책

앱은 작업 성격과 하네스 단계에 따라 Claude와 Codex 모델을 자동 추천한다.

작업 시작 전 다음 정보를 표시한다.

* 선택된 Claude 모델
* 선택된 Codex 모델
* 각 모델이 담당하는 단계
* 선택 이유
* 예상 비용 등급
* 예상 호출 규모
* 사용자가 변경할 수 있는 대안

비용 표시는 정확한 금액을 보장하지 않는다.

가격 또는 사용량 정보가 공식 CLI에서 제공되지 않는 경우 다음처럼 추정치임을 표시한다.

* 낮음
* 보통
* 높음

## 10.1 실행 중 모델 변경

실행 중에는 모델을 임의로 변경하지 않는다.

다음 사유가 있을 때만 변경을 제안한다.

* 모델 실행 실패
* 컨텍스트 한도 초과
* 필요한 기능 미지원
* 반복적인 도구 호출 실패
* 응답 품질이 완료 조건을 충족하지 못함

사용자 승인 없이 더 비싼 모델로 자동 상향하지 않는다.

## 10.2 프로젝트별 고정

프로젝트별 Claude 및 Codex 모델 고정 설정을 지원한다.

프로젝트 고정 설정은 자동 추천보다 우선한다.

# 11. 모델 간 컨텍스트 전달

Claude와 Codex 사이에 전체 대화를 그대로 전달하지 않는다.

작업별로 구조화된 Context Package를 생성한다.

## 11.1 Context Package 내용

```text
Context Package
├─ 작업 ID
├─ 프로젝트 및 worktree 경로
├─ 기준 브랜치와 기준 커밋
├─ 확정 요구사항
├─ 완료 조건
├─ 설계 결정과 근거
├─ 변경 금지 사항
├─ 승인된 작업 범위
├─ 관련 파일
├─ 관련 심볼과 코드 위치
├─ 작업 계획
├─ 현재 진행 단계
├─ 필요한 diff
├─ 빌드·테스트 결과
├─ 이전 실패 가설 및 수정 이력
├─ Claude 리뷰 결과
└─ 미해결 위험
```

원본 대화는 요구사항 해석에 반드시 필요한 관련 구간만 첨부한다.

각 모델은 Context Package만 신뢰하지 말고 동일 worktree의 실제 파일을 직접 읽어 확인해야 한다.

Context Package의 생성, 수정, 전달 내용은 작업 기록에 저장한다.

저장 전 민감정보를 마스킹한다.

## 12.3 항상 차단할 작업

* 인증 토큰 출력 또는 추출

* 계정 한도 우회
* 승인 없는 회사 데이터 외부 전송
* SSH 개인키 원문 출력
* 시스템 인증 저장소 비밀값 노출
* 악성 코드 실행
* 승인 정책 자체를 AI가 비활성화하는 행위

# 13. 네트워크 정책

외부 네트워크는 기본 안전 목록을 기반으로 제어한다.

## 13.1 읽기 요청

다음 범주의 승인된 도메인은 자동 접근할 수 있다.

* 공식 언어 문서
* 공식 프레임워크 문서
* 공식 패키지 저장소
* 공식 패키지 메타데이터
* GitHub 공개 저장소 읽기
* OpenAI 공식 문서
* Anthropic 공식 문서
* 프로젝트에 등록된 사내 문서
* 사용자가 명시적으로 허용한 도메인

허용 목록 밖의 도메인은 사용자 승인을 요청한다.

## 13.2 쓰기 요청

모든 네트워크 쓰기 작업은 사용자 승인을 받아야 한다.

예:

* Git push
* PR·이슈·릴리스 생성
* 파일 업로드
* 로그 또는 diff 업로드
* 외부 API에 프로젝트 데이터 전송
* 패키지 게시
* 배포
* 이메일·메신저·웹훅 전송
* 원격 서버 설정 변경

승인 화면에는 다음을 표시한다.

* 목적지
* 요청 방식
* 전송 목적
* 전송될 데이터 요약
* 민감정보 포함 가능성
* 예상 외부 부작용

리디렉션으로 허용 목록 밖 도메인으로 이동하면 자동 접근을 중단한다.

읽기 요청이 쓰기 요청으로 바뀌면 다시 승인을 요청한다.

# 14. 패키지 설치 정책

## 14.1 자동 허용

다음 조건을 모두 만족하는 복원 설치는 자동 허용한다.

* 기존 manifest에 선언됨
* 기존 lockfile에 버전이 고정됨
* lockfile을 변경하지 않음
* worktree 또는 프로젝트 전용 환경에서 실행
* 전역 설치가 아님
* 회사 장비 정책에 위배되지 않음

예:

* `npm ci`
* `pnpm install --frozen-lockfile`
* `yarn install --immutable`
* `cargo fetch`
* 기존 잠금 파일을 존중하는 언어별 복원 명령

실제 지원 명령은 프로젝트 종류에 따라 안전하게 판정한다.

## 14.2 승인 필요

* 새 패키지 추가
* 패키지 삭제
* 버전 변경
* 패키지 출처 변경
* lockfile 생성 또는 재생성
* lockfile 대규모 갱신
* 전역 설치
* 설치 스크립트 실행
* 시스템 도구 체인 설치
* 시스템 환경 변경

승인 전에 다음 내용을 표시한다.

* 패키지명
* 버전 또는 버전 범위
* 출처
* 직접 의존성 여부
* 주요 전이 의존성
* 변경될 manifest
* 변경될 lockfile
* 설치 스크립트 존재 여부
* 실행할 실제 명령
* 예상 보안·빌드·호환성 영향

회사 장비에서는 사내 패키지 레지스트리, 프록시, 인증서, 허용 목록과 보안 정책을 최우선으로 적용한다.

# 15. 테스트 및 자동 수정 정책

Codex 구현 후 프로젝트에서 사용 가능한 검증 명령을 식별해 실행한다.

가능한 검증 항목:

* 포맷 검사
* 린트
* 타입 검사
* 단위 테스트
* 통합 테스트
* 빌드
* 프로젝트별 추가 검증

## 15.1 테스트 실패 자동 수정

테스트가 실패하면 Codex가 원인을 분석하고 최대 2회까지 자동 수정 및 재실행한다.

각 시도는 이전 시도와 다른 원인 가설을 가져야 한다.

시도별로 다음을 기록한다.

* 실패한 명령
* 실패 테스트
* 오류 메시지
* 원인 가설
* 가설의 근거
* 수정 내용
* 변경 diff
* 재실행 결과
* 남은 위험

동일한 수정 또는 동일한 원인 가설을 근거 없이 반복하지 않는다.

## 15.2 자동 수정 금지 대상

다음 변경이 필요하면 자동 수정하지 않고 즉시 사용자에게 보고한다.

* 테스트 삭제
* 테스트 비활성화
* assertion 완화
* 통과 기준 완화
* 요구사항 변경
* 완료 조건 변경
* 아키텍처 변경
* DB 스키마 변경
* 인증·보안 변경
* 네트워크 정책 변경
* 외부 전송 변경
* 데이터 손실 가능 작업
* 승인 범위 밖 대규모 리팩터링

동일 실패가 반복되거나 2회 이후에도 실패하면 작업을 중단한다.

중단 보고서에는 다음을 포함한다.

* 가장 가능성 높은 실패 원인
* 시도별 가설
* 전체 변경 diff
* 실행 로그
* 남아 있는 위험
* 다음 권장 조치

# 16. Claude 최종 리뷰 정책

Codex 구현과 테스트가 완료되면 Claude가 최종 리뷰를 수행한다.

Claude는 실제 worktree의 파일과 Git diff를 직접 확인한다.

리뷰 항목:

* 요구사항 충족 여부
* 완료 조건 충족 여부
* 오류 가능성
* 기존 기능 회귀
* 데이터 손실 위험
* 인증·권한 취약점
* 민감정보 노출
* 승인되지 않은 네트워크 동작
* 리소스 누수
* 동시성 문제
* 테스트 충분성
* 변경 범위 준수

## 16.1 심각도

최소 다음 등급을 사용한다.

* Critical
* Major
* Minor
* Suggestion

## 16.2 중대 문제 자동 재수정

Critical 또는 Major 문제만 자동 재수정 대상으로 한다.

Claude는 코드를 직접 수정하지 않는다.

Claude가 다음 구조로 Codex에 수정 요청을 전달한다.

```text
문제 위치
문제 설명
심각도
재현 또는 근거
위험
반드시 지켜야 할 수정 조건
변경 금지 범위
필수 재검증 항목
```

Codex의 자동 재수정은 최대 1회다.

재수정 후 관련 테스트와 회귀 테스트를 다시 실행하고 Claude가 재검토한다.

다음 변경이 필요하면 자동 재수정하지 않는다.

* 아키텍처 변경
* DB 변경
* 보안 정책 변경
* 네트워크 변경
* 요구사항 변경
* 데이터 손실 가능 작업
* 승인 범위 확대

재검토에서도 중대 문제가 남으면 병합을 차단하고 사용자에게 보고한다.

Minor와 Suggestion은 자동 수정하지 않고 최종 권고사항으로 표시한다.

# 17. 사용자 diff 검토 및 병합

모든 구현과 리뷰가 완료되면 사용자에게 다음을 표시한다.

* 변경 요약
* 변경 파일 목록
* 파일별 diff
* 빌드 결과
* 테스트 결과
* Claude 리뷰 결과
* 자동 수정 이력
* 미해결 Minor·Suggestion
* 알려진 위험
* 병합 대상 브랜치
* 병합 방식

사용자 승인 전에는 원본 브랜치에 병합하지 않는다.

## 17.1 병합 방식

사용자가 승인하면 기본 브랜치에 자동 병합한다.

병합 전에 다음을 다시 확인한다.

* 원본 브랜치 변경 여부
* 기준 커밋 이후 새 변경 존재 여부
* worktree 상태
* 미커밋 변경 존재 여부
* 테스트 상태
* 리뷰 상태

## 17.2 병합 충돌

다음과 같은 안전한 충돌만 AI가 자동 해결할 수 있다.

* 서로 다른 코드 블록의 비중첩 변경
* import 또는 use 문 정리
* 포맷 차이
* 생성 파일의 결정적 재생성
* 의미 변화가 없는 순서 변경

자동 해결 후 반드시 테스트를 다시 실행하고 사용자에게 결과를 표시한다.

다음 충돌은 자동 해결하지 않는다.

* 동일 로직의 상충 변경
* 설정값 충돌
* 삭제 대 수정 충돌
* 스키마 충돌
* 보안 정책 충돌
* 의존성 버전 충돌
* 의미를 확정할 수 없는 충돌

이 경우 병합을 중단하고 사용자에게 수동 해결을 요청한다.

* SQLite 작업 레코드
* 로그
* diff
* 테스트 결과
* 첨부파일

* 미병합 worktree
* 사용자가 보존 표시한 작업

정리 작업은 앱 시작 시와 하루 1회 수행할 수 있다.

고아 파일을 함께 정리하고 삭제 결과만 최소 감사 로그로 남긴다.

# 21. 애플리케이션 업데이트

공식 릴리스 서버에서 업데이트를 자동 확인한다.

자동 확인은 허용하지만 다운로드 및 설치는 항상 사용자 승인을 받아야 한다.

사용자에게 다음을 표시한다.

* 현재 버전
* 새 버전
* 변경사항
* 보안 중요도
* 호환성 정보
* 데이터베이스 마이그레이션 여부
* CLI 호환성
* 예상 영향

설치 전 다음을 수행한다.

* 공식 패키지 서명 검증
* 해시 검증
* 현재 실행 파일 백업
* 설정 백업
* SQLite 데이터베이스 백업
* 저장소 스키마 버전 기록

업데이트 후 다음을 검사한다.

* 앱 시작 성공
* DB 마이그레이션 성공
* 설정 로딩 성공
* 기본 무결성 검사
* CLI 탐지 기능

실패하면 이전 버전으로 자동 롤백한다.

## 21.1 업데이트 보류 조건

* 진행 중인 AI 작업
* 실행 중인 명령
* 미병합 작업
* 복구 대기 세션
* 미커밋·미추적 변경이 있는 worktree
* 데이터베이스 백업 실패
* 서명 또는 해시 검증 실패
* 회사 장비 정책과 충돌

회사 장비에서는 사내 배포 및 보안 정책을 앱 자체 업데이트 정책보다 우선한다.

# 23. 상태 머신

작업 상태를 문자열로 임의 관리하지 말고 명시적인 상태 머신으로 설계한다.

예시 상태:

```text
Created
ProjectValidated
AwaitingGitInitApproval
GitInitialized
WorktreeCreating
WorktreeReady
PlanningWithClaude
AwaitingDesignApproval
ImplementingWithCodex
Testing
AutoFixing
ReviewingWithClaude
ReviewFixing
AwaitingUserDiffApproval
Merging
MergeConflict
PostMergeTesting
Completed
Paused
Failed
RecoveryRequired
UnknownExternalEffect
Cancelled
CleanupPending
Archived
```

각 상태에서 허용되는 명령과 다음 상태를 정의한다.

앱 재시작 후에도 상태가 복원돼야 한다.

상태 전이는 트랜잭션 방식으로 저장하고, 장시간 작업 전후에 체크포인트를 기록한다.

# 24. 보안 설계 원칙

* 최소 권한
* 기본 거부
* 명시적 승인
* 원본 프로젝트 격리
* 인증정보 비보유
* 비밀값 저장 전 제거
* 외부 전송 가시성
* 감사 가능성
* 복구 가능성
* 파괴적 작업 차단
* 회사 정책 우선
* 사용자 승인 없는 비용 상승 금지

AI 출력은 신뢰할 수 없는 입력으로 취급한다.

AI가 생성한 명령을 문자열 그대로 셸에 넘기지 말고 다음 절차를 거친다.

```text
명령 파싱
→ 실행 파일 식별
→ 인수 분리
→ 정책 판정
→ 경로 검증
→ 위험도 판정
→ 필요 시 승인
→ 구조화된 프로세스 실행
```

가능하면 셸 문자열 실행보다 프로그램과 인수 배열을 분리해 실행한다.
